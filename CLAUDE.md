# MaKlaude

## Goal

Build MaKlaude — an autonomous system for operating Kubernetes clusters on a human's behalf.

MaKlaude continuously watches the health of one or more clusters a human has put under its care: it detects problems, diagnoses root causes, and safely fixes what it confidently can. Anything risky or destructive it does NOT do on its own — it escalates to a human with enough context to decide, and acts only once approved. Throughout, it keeps humans informed through whatever channel they prefer (Slack, email, GitHub, etc.) so there's always a clear, auditable trail of what it saw, what it did, and what it's waiting on.

Guiding principles, not a blueprint — you decide the actual architecture, agents, and tools:
- Safety first. Read/diagnose freely; gate every mutating or destructive action behind explicit human approval until trust is earned. Least privilege everywhere.
- Multi-cluster from the start. A human can register several clusters; MaKlaude operates them without cross-contamination.
- Extensible. New operational capabilities (e.g. security/vulnerability scanning, cost and capacity awareness, GitOps-aware remediation) should be addable over time without redesign.
- Human-in-the-loop, not human-replaced. MaKlaude augments operators; it never silently takes irreversible action.

Important boundary: humans configure which clusters MaKlaude monitors and operates, and supply the credentials/access. Building that configuration surface and the operational system is your job; standing it up against real clusters is the human's job once it's built.

Treat the well-known "multi-agent Kubernetes DevOps" pattern (a coordinator delegating to specialized analyze / remediate / communicate roles) as inspiration only — feel free to surpass it. Aim higher than a minimal demo: build something an operator would actually trust with real clusters.




## Meta-Concepts

These are the principles this dev system operates by. Evolve them as the project matures.

- **GitHub as coordination layer** — issues track progress, PRs deliver changes, CI/CD enforces quality. Humans and agents speak the same protocol.
- **Quality gates and e2e testing** — code, tests, CI/CD, deployment are all first-class concerns.
- **Self-improvement** — continuously evolve agents, skills, and strategies.
- **Self-monitoring** — monitor progress, detect stuck/looping states, try to unblock, escalate to human when stuck.
- **Minimal human-in-the-loop** — do everything possible autonomously. Highlight what requires human action and offer to do it if given access.
- **Deterministic over agentic** — if a task is well-understood and doesn't need LLM judgment, build a deterministic tool (script, CLI, CI step). Reserve LLMs for fuzzy reasoning.
- **Incremental planning** — only detail the current milestone. Future milestones stay high-level until they're next.

## Agent Roster

- **Onboarding** — refines goal with human, produces milestones (runs once at project start)
- **Project manager** — owns roadmap, tracks progress, drills down current milestone into tasks
- **Human interaction** — all comms with user (reports, escalations, access requests). Speaks A2H protocol.
- **Evolver** — evolves the dev system itself (new agents, tools, skills, memory design, CLAUDE.md refinement). Escalates framework-level improvements to genesis.
- **Health / self-review** — monitors for stuck/looping, audits quality
- **Workers** — designed by the dev system for the specific goal

## Execution Model

GitHub Actions serve as the trigger layer:
- **Scheduled workflows** (cron) — periodic advancement of project state
- **Event-triggered workflows** — issue/PR events, human feedback, comments

Each trigger launches a Claude Agent SDK session as the orchestrator.

## Learnings

Curated memory — non-obvious lessons so future sessions don't relearn them. The evolver maintains this.

### Health detection
- **Pod container state oscillates; don't detect crashloop on instantaneous state.** A crashlooping pod cycles `Waiting(CrashLoopBackOff)` → `Running` → `Terminated(Error)` → back, so a point-in-time scan keyed only on `state.waiting.reason == "CrashLoopBackOff"` misses it about half the time — and the same race bites a real interval scan, not just the e2e. Detect on a *stable* signal: instantaneous `CrashLoopBackOff` **OR** `RestartCount >= 2` with a non-zero last/current termination. See `internal/health/collector.go` (`containerCrashLooping`) + regression test `TestCollect_CrashLoopMidCycle`.

### Dev system
- **Agent turn budgets fail silently, and the floor must move for the CLASS, not the runner that failed.** A Claude-invoking workflow with too low a `--max-turns` doesn't error usefully — it dies at `error_max_turns`, and the only visible trace is a safety-net escalation issue. This has now bitten five times: evolver at 20 (#38), events orchestrator at 20 (#81, died mid-task on #78/PR #79), evolver at 30 (#85, died with *no* artifact — no branch, PR, issue, or comment), scheduled orchestrator at 40 (#87, died at turn 41 seconds after opening PR #86 — deliverable escaped, bookkeeping truncated), evolver at 45 (#96, died at turn 46 seconds after PR #95 merged — same shape as #87). Each of the first three fixes raised only the runner that happened to fail, so the class floor stayed put and the next-tightest runner failed next. **Generalizable rule: when a shared failure mode recurs on a different member each time, raise the guard for the shape, not the instance.** A second-order trap follows from it: #89 *did* move the class floor, but set it to 40 — a value already on the observed-failure list — so the class recurred anyway. **A floor must sit strictly above every budget ever observed to fail**, which is now mechanical rather than remembered: `budgetsFailedBeforeDelivering` in `test/devsystem/workflows_test.go` is append-only history and `TestOrchestratorFloorExceedsObservedFailures` fails the build until the floor clears it. (That list was originally one undifferentiated `observedFailedBudgets`; the split, and why only the before-delivering class may move a floor, is two bullets down.) Floors now: orchestrator-class (open-ended agent definition — assess, read issues/PRs, dispatch subagents, complete a unit of work) **60 minimum**; narrow fixed-procedure agents like auto-merge keep a deliberately small budget (15) so needing more turns fails fast. The same test also fails on a Claude-invoking workflow that isn't classified. Two corollaries: (1) a run that dies at max-turns *may still have landed its work* — check for a pushed branch/PR before treating the escalation as "nothing happened" (#87's fix was merged by auto-merge while the escalation sat open; #96 likewise landed PR #95 and its #81 comment before dying); (2) budgets are a symptom, and raising them did not converge in six attempts — see the next bullet for where that ended up.
- **Anything a human must receive cannot live inside an agent's turn budget.** This is what #97 concluded after six budget raises and five deaths, and it retires two dead ends explicitly. The last two failures had a signature the first three didn't: *the deliverable landed and only the bookkeeping was truncated* (#87 died seconds after opening PR #86; #96 seconds after merging PR #95). Implementation cost is unbounded — it scales with whatever task the run picks up, chosen *during* the run — while wrap-up is small and constant, so sharing one budget lets the unbounded term crowd out the only part with external value. **Dead end 1: raising the number.** No number is safe against an unbounded term. **Dead end 2: splitting coordinator from worker** (the proposal in #97) — rejected, because in both observed failures it was the *coordinator's own* work (assess → verify → report) that got truncated, so moving implementation elsewhere fixes nothing; it also rests on an unverified premise (whether subagent turns share the parent's `--max-turns` pool in `claude-code-action` — still unknown, deliberately made non-load-bearing), and a dispatched worker run that never starts reintroduces #84's silent stall at a new layer. **What worked instead is the shape #84 already found**: `nudge-gates.sh` runs *before* the agent step so the signal escapes a max-turns death, and `escalate.sh` now runs *after* one — it queries the REST issues endpoint (`since` + `sort=updated`, **never** the search API, which is index-lagged and would miss artifacts created seconds ago) and lists every issue/PR the dying run touched. So corollary (1) above is no longer a rule an agent must remember; the escalation states it. Guarded by `test/devsystem/escalate_test.go`: membership (every `anthropics/claude-code-action` workflow has an `if: failure()` escalate step) plus content. Full reasoning in `.genesis/design/agent-turn-budgets.md`. **When a max-turns death recurs, the question is no longer "what budget?" but "did the human-facing output escape the budget?"**
- **Intent is the one output that can't leave the budget, so it moves to the front of it instead.** The bullet above predicted the next failure would be the agent's *reasoning*, and #101 delivered it: the evolver died at max-turns again *after* artifact discovery shipped, so triage correctly found PR #100 already landed — but nothing said why that run chose that work, and a run that dies with **no** artifact (#85) gets nothing from artifact discovery at all. Every other human-facing output was fixable by moving it *outside* the agent step (`nudge-gates.sh` before, `escalate.sh` after); intent can't be, because only the agent knows it. So it gets position rather than placement: `.genesis/scripts/checkpoint.sh` is the agent's **first** write, before the unbounded implementation work that is what actually exhausts the budget, and `escalate.sh` renders it as "What this run was trying to do" above the landed-artifacts section. Three things that make it work and are easy to get wrong: (1) **a file in `$RUNNER_TEMP`, not an issue comment** — intent only matters when the run fails, so commenting every run would post a paragraph nobody reads every six hours, and a file needs no token and no network, meaning the checkpoint can't 502 and manufacture the false escalation #91 removed; (2) **`checkpoint.sh --path` is the single source of truth for the location** — `escalate.sh` asks the script instead of recomputing the default, because two scripts deriving one shared path drift and the symptom is "no intent recorded" printed while the file sits on disk; (3) **absence is reported, not omitted** — "No intent checkpoint was recorded" plus no artifact *is* the #85 signature, and a human needs to be told which happened. Guarded by `test/devsystem/checkpoint_test.go`, whose scope is drawn from the existing `minTurns` map rather than a new list: a workflow at `orchestratorClassFloor` is by definition one whose work is chosen *during* the run, so narrow fixed-procedure runners (`genesis-merge.yml`) are exempt *by classification* — its intent is its prompt — and one classification feeds both guards. **Generalizable rule: when an output can't be moved out of a bounded resource, move it to the front of it — and when you must exempt members from an invariant, derive the exemption from an existing classification rather than writing a second list.** The instruction lives in the workflow prompts; mirroring it into `.claude/agents/*.md` was declined by the same `.claude/` write restriction that blocks fixing `evolver.md` step 4. What's still unrecoverable is the *middle* of a dying run — the dead ends it burned turns on — which is transcript retention, not budgets or topology.
- **A guard whose *check* is mechanical but whose *input* is remembered is only as fresh as the agent feeding it — and this one was fed by the agent that kept dying.** `observedFailedBudgets` in `test/devsystem/workflows_test.go` was built so "the floor must exceed every budget observed to die at max-turns" would be enforced by the build rather than by memory. The check was mechanical; **appending** to it never was. So when the evolver died at `--max-turns 60` on 2026-07-28 (run 30353938690, `num_turns: 61`, #101) — 60 being the current `orchestratorClassFloor` — nothing appended it, and `TestOrchestratorFloorExceedsObservedFailures` stayed green through four consecutive failing evolver runs (30, 30, 45, 60; Jul 25–28). The test asserted a fact that was true only because its data was stale. **Ask of any append-only history: who appends, and what happens when that actor is the thing being measured?** The second finding is why the answer wasn't raise #7: the list conflated two failure classes with opposite fixes. Sorted by whether the deliverable landed, 20/20/30 (#38, #80/#81, #85) died *before* producing anything — a real budget shortfall, and a floor fixes it — while 40/45/60 (#87, #96, #101) died *seconds after* their PR landed, which is evidence about the unbounded implementation task the run chose mid-run, not about the number. For any floor `N` some task overruns it, so feeding wrap-up truncations into the floor is what made five raises look justified and none of them converge. Now split: `budgetsFailedBeforeDelivering` drives the floor (max 30, so 60 stands honestly), `budgetsFailedDuringWrapUp` is recorded and explicitly does not, `TestBudgetFailureClassesAreDisjoint` blocks the "append to both to be safe" shortcut that would silently force the raise anyway, and `escalate.sh` states the classification *in the escalation* — deliverable listed → "this is a wrap-up truncation, do NOT raise `--max-turns`"; nothing listed → the #85 signature, append to the list that does move the floor. Artifact discovery (#97) gave a human the facts and left the inference open; the inference had been drawn wrong six times, so it isn't left open any more. **Generalizable rule: when one number is fed by two failure classes with opposite fixes, no value of it converges — split the evidence before tuning the knob.** Also measured while looking: the transcript really is absent from run logs (`init` + `result` only, 469 lines, zero tool calls), and `claude-code-action`'s `show_full_output: true` would add it — but it streams tool results and this repo is **public**, where run logs *and* artifacts are world-readable and Actions masks only registered secrets. Transcript retention needs redaction or a private sink first; it is cheap to enable and not cheap to enable safely.
- **The transcript was never missing — it was discarded. Check whether the artifact already exists before designing a way to produce it.** #106 closed the last gap in the max-turns series: intent (#102) says what a run meant to do and artifact discovery (#97) says what it produced, but neither says where the turns *went* — which approaches it tried, which dead ends it burned. #104 measured the run log at 469 lines with **zero tool calls** and framed the fix as enabling `claude-code-action`'s `show_full_output`, which on this **public** repo means world-readable tool results and allowlist-hard redaction — expensive and risky. That framing was wrong about the premise: `base-action/src/run-claude-sdk.ts` already writes every SDK message to `$RUNNER_TEMP/claude-execution-output.json`, **on the error path as well as the success path** (an `error_max_turns` run still emits a `result`, and the `catch` writes too), so the full transcript is complete on disk when a run dies and is then thrown away with the runner. Retention is therefore a *copy*, not a capture: `.genesis/scripts/retain-transcript.sh` ships it to the private Loki sink already wired for activity logging, `show_full_output` stays off, and nothing world-readable gains content. Three properties are guarded by execution rather than review in `test/devsystem/transcript_test.go`, because "no leak" is a claim about what a process emits and reading shell for it is how leaks happen on public repos: the sink receives reasoning + tool name + tool input + tool result; **stdout/stderr receive none of them** (that is the Actions log); and Loki entries carry unique increasing nanosecond timestamps with low-cardinality labels (the duplicate-drop-acked-204 loss `log.sh` already ate). Placement follows the series' own rule — `always()`, after the agent step (the file doesn't exist before it) and *before* `escalate.sh`, which renders the retention status so a human is told in the same breath whether the transcript survived and the LogQL to read it; absence is reported, not omitted. **Generalizable rule: when a diagnostic seems to require turning on an expensive or unsafe capture, first check whether the tool already produces it somewhere ephemeral — moving an existing artifact is cheaper and safer than generating a new one.**
- **Splitting a population is only sound once you've established every member belongs to it — classify the death before routing its evidence.** #104's split is the fix that ended six non-converging budget raises: deliverable landed → `budgetsFailedDuringWrapUp` (does not move the floor), nothing landed → `budgetsFailedBeforeDelivering` (mechanically does). The branches are right. What was never checked is the *precondition*: `escalate.sh` applied the split to **every** failure, and its only input — artifact presence — cannot tell a max-turns death apart from a run that never reached the model, because both produce an empty artifact list. #108 and #109 are the bill. Both died `subtype: success, is_error: true, num_turns: 1, total_cost_usd: 0` — one turn against a budget of **60**, zero dollars, and a near-identical ~177–179s across two workflows nine hours apart (a client-side retry budget exhausting, not a run doing work) — and both escalations printed the #85-signature note telling a reader to append 60 to `budgetsFailedBeforeDelivering`. That is raise #7 from non-budget evidence, and it does not even fail cleanly: 60 already sits in `budgetsFailedDuringWrapUp`, so the append also trips `TestBudgetFailureClassesAreDisjoint` and leaves two contradictory red tests. Fixed by `.genesis/scripts/run-outcome.sh`, which classifies `max-turns` / `agent-error` / `agent-ok` / `no-agent-output` from the terminal `result` message and gates the split on a confirmed `error_max_turns`; **every other class must actively say "do NOT append to either list", because saying nothing about the budget is exactly what let the #85 note run on evidence that never supported it.** Three things this cost nothing to get right and would have been expensive to get wrong: (1) the evidence was never missing — the same `$RUNNER_TEMP/claude-execution-output.json` that #106 found for transcripts carries the terminal result, and `retain-transcript.sh` already reads it one step earlier, so this is the *third* consecutive fix in this series that turned out to be a read of an artifact the tool already produces; (2) the classifier emits **only bounded scalars** (sanitized subtype token, one bool, three numbers) because escalation issues are world-readable and the SDK's free-form `result`/`error` strings can echo prompts and tool output — the leak `show_full_output` was left off to avoid, and an unrecognized subtype degrades to `unparseable` rather than being echoed; (3) **How this run died** renders *above* intent and artifacts, since every section below reads differently depending on the answer and putting it last is how a reader reaches the #85 note before learning the run used one turn. Guarded by execution in `test/devsystem/runoutcome_test.go` — all four classes, the leak marker planted in `result`/`error`/`subtype`, `--class` agreeing with line 1, and membership over `escalate.sh`. **Note the family resemblance: #104 found a guard whose *check* was mechanical but whose *input* was remembered; this is a classifier whose *branches* were mechanical but whose *precondition* was assumed. When a mechanism keeps producing wrong answers from correct logic, the bug is upstream of the logic.**
- **A correctly-waiting run is still a stalled project — gate staleness must be deterministic.** The plan/completion gates' failure mode is *silent indefinite stalling*, and it's the one failure mode no safety net covered: `automation:failure` catches runs that **die**, nothing catches runs that **succeed at doing nothing**. Milestone 4's plan gate (#76) sat `needs:human` for 21 days across ~85 scheduled ticks; every run correctly obeyed "if a `needs:human` plan issue is open, do nothing and wait", so every run did nothing, said nothing, and left no trace. `main` was green the whole time. The guideline "escalate if stuck more than 2 cycles" never fired because "stuck" required an LLM to compare `createdAt` against today and *choose* to care — it finally went out on day 21 by chance. "Is this gate older than N days" needs no judgment: `issues.sh gates`/`stale-gates` report age, `summary` always prints a **Human Gates** section, and `nudge-gates.sh` posts exactly one nudge per gate (marker label `nudged:stale`), wired **before** the agent step in `genesis-orchestrator.yml` so the signal escapes even if the agent dies at max-turns. Guarded by `test/devsystem/stalegates_test.go`. Generalizable rule: **when a hard rule tells an agent to do nothing, something deterministic must still measure how long it's been doing nothing.**
- **An opt-in invariant is not an invariant — test the membership, not the member.** Serializing the repo-mutating agents is done with a shared `concurrency.group`, which every workflow must opt into individually. The evolver never did, so two Claude sessions ran fully in parallel on this repo — the exact "two orchestrators duplicating work" case the group exists to prevent. It held for the entire sampled history (15/15 days; 2026-07-27 the two runs started **2 seconds** apart) and produced no failure, no red CI, and no escalation, because parallel agents don't error — they just race on pushes, issues and PRs. The trigger was a *cron collision*: *GitHub dispatches all of a repo's crons that share one expression in the same batch and then delays that batch by the same 1.5–3.5h*, so `0 6 * * *` (evolver) and `0 */6 * * *` (orchestrator) landed together to the second. Writing a different hour is what decorrelates them; both properties are now guarded by `test/devsystem/concurrency_test.go` (group membership per workflow + no two genesis crons sharing a firing minute). Two things worth knowing: (1) `cancel-in-progress: false` still lets GitHub cancel an *older pending* run when a newer one queues into the group, and a run cancelled while pending never starts a job — so it cannot trip `if: failure()` and is invisible. Cron staggering was believed to keep that window small; it does not — the window is dominated by *event* bursts, not cron collisions, and the next bullet has the measurement and the actual fix. (2) **Generalizable rule: when a safety property depends on every member of a set opting in, the thing to test is the set.** Same shape as the turn-budget floors above — an unclassified workflow fails the test rather than silently defaulting to unsafe.
- **A concurrency group has exactly one pending slot, and a run with nothing to do will take it. Gate before group.** GitHub keeps at most **one** pending run per group and cancels the older pending one when a newer arrives — and a *workflow-level* `concurrency:` is joined **before any job's `if:` is evaluated**. So a run destined to skip still occupies the slot and evicts a run that has real work. Every event-triggered workflow here had this, and the cost was total: **Genesis CI Failure Triage had 0 successes in 157 runs** — the loop's wake-on-CI-failure net never fired once. On 2026-07-05 the only genuine CI failure in the repo's history (run 28736219761, 09:29:04) queued a triage run that was evicted at 09:31:08 by a no-op trigger that would have skipped in one second; the PR was never triaged. Events orchestrator: 132 cancelled vs 12 succeeded. Auto-merge: 10 cancelled, the same green-but-unmerged outcome its separate group was created to prevent — a separate group bounds *who* can evict you, not *whether you evict yourself*. The fix is one line of placement: declare `concurrency:` on the **job**, under the `if:`, so a gated-out run exits in ~1s without ever queueing. Guarded by `TestGatedWorkflowsJoinGroupBelowTheirGate` in `test/devsystem/concurrency_test.go` — membership over every Claude-invoking workflow, and it immediately found the auto-merge instance nobody had looked for. Note this also completes bullet (1) above: because a run cancelled *while pending* starts no job, it cannot trip `if: failure()`, so **none of these 238 losses produced an escalation, a red check, or any trace at all** — the same invisible-nothing-happened class as the stale-gate stall, and the reason a count is worth taking rather than a comment asserting the window is small.
- **Work derived from an event payload is destroyed by supersession; work derived from repo state self-heals.** This is why the eviction above was unrecoverable rather than merely late, and it is the load-bearing distinction when deciding whether a dropped trigger matters. The scheduled orchestrator survives being evicted fine — it re-reads global state, so a later tick does the same work. `genesis-ci-failure.yml` cannot: it can only triage the run named in `github.event.workflow_run`, and the run that *wins* the pending slot carries a **different** payload (usually a passing check), so it skips. The failure's triage never existed and no later run reconstructs it. **So for any event-triggered work, ask whether the next scheduled tick could re-derive it from repo state; if not, the trigger is a single point of failure and needs a state-derived backstop.** Here that is `issues.sh red-prs` — open PRs with failing checks, stalest first, printed unconditionally by `issues.sh summary` (which every run reads) alongside the Human Gates section. Same shape as #84's lesson one layer out: the gates fix made *elapsed time* deterministic, this makes *dropped work* deterministic. Guarded by `test/devsystem/redprs_test.go`, whose false-positive cases matter as much as the detection ones — this prints every tick, and a backstop that cries wolf is one the orchestrator learns to skip.
- **The framework-escalation path in `evolver.md` does not work: `Sayfan-AI/genesis` is read-only for this bot.** `.claude/agents/evolver.md` step 4 tells the evolver to open an issue on genesis with label `needs:evolver`. Reads succeed (`gh issue list/view`, labels), so the path looks live right up until the write: `gh issue comment` fails with `GraphQL: Resource not accessible by integration (addComment)`, and `issue create` uses the same scope (verified 2026-07-27). **Until access is granted, post framework-level findings as a comment on #81** — the upstream-carry tracker — written as if they were the genesis issue: what broke, proposed fix, and the paths on `main` a human can lift verbatim. Two things that make the escalation actually land: check `gh issue list --repo Sayfan-AI/genesis` first (readable) and, if an issue already exists but is *narrower* than what you found, say precisely what it misses rather than restating it — e.g. genesis #22 proposed the concurrency group for two workflows and missed both the evolver and the cron collision above. #81 records what access would unblock this. The stale step-4 instruction itself still needs correcting; that edit was declined this cycle.
- **Auto-merge is bot-only on purpose; the orchestrator merges human PRs.** `genesis-merge.yml` merges only `genesis-dev-bot[bot]` PRs. The repo is public, so `pull_request` fires for fork PRs from anyone — auto-merging "any green PR" would let an arbitrary contributor land on main unreviewed. Accepted consequence: a **human-authored** PR is not auto-merged. The orchestrator merges it on the run that follows (the PR event, or the next scheduled tick) after verifying checks are green and no `needs:human` label is set; if the diff is large, ambiguous, or safety-critical, it comments, labels `needs:human`, and stops instead. So human PRs land one run late by design — that lag is not a bug.
- **Every safety net here reports *problems*; the last invisible thing was a piece of work that was finished.** The invisible-nothing-happened class has been drained one member at a time — a gate that waits forever (#84), a triage event dropped by supersession (#100), a run that dies mid-task (#97/#106/#110) — and each fix made a *failure* deterministic. #112 is the same class with the sign flipped: a green, `MERGEABLE`/`CLEAN`, non-draft, human-authored PR is not a failure at all, and it was still invisible, because `summary` had a Red PRs section and no counterpart. The bullet above says the orchestrator merges human PRs "on the run that follows" — but that depended on a run *happening to notice*, and nothing put the PR in front of one: close its tracking issue early, or open it with no linked issue, and it is unreachable from every section of the report each run reads. The fix is the shape the other three converged on — derive from repo state, print unconditionally, empty means all-clear: `issues.sh ready-prs`, stalest first, in a **Ready to Merge** section. Two details worth keeping: (1) **the exclusions carry more weight than the detections**, because this prints every tick and a backstop that cries wolf is one the orchestrator learns to skip — so draft, any pending check, missing checks, `BEHIND`/`BLOCKED`/`DIRTY`/`UNKNOWN`, `needs:human`, and bot authors (auto-merge owns those; listing them races it) are each their own test case in `test/devsystem/readyprs_test.go`; (2) **`mergeStateStatus == CLEAN` is not sufficient on its own** — GitHub reports `CLEAN` when no branch protection *requires* the failing check, so a red PR passes that test and the check verdicts must be read independently. Requiring every check to have concluded `SUCCESS` (rather than merely "not failed") is also what makes `ready-prs` and `red-prs` provably disjoint, which is asserted rather than assumed. **Generalizable rule: when auditing what a report makes visible, enumerate the states that need a human or an agent to *act*, not the states that are broken — "done and waiting" is an actionable state that no error-shaped net will ever surface.**

### Testing / CI
- **Local kind on macOS is NOT a faithful proxy for CI on Linux — CI is the source of truth.** macOS Docker Desktop remaps bind-mount ownership to the host user, so a root-written file (e.g. the apiserver audit log) is readable locally but `root:0600` and unreadable by the non-root runner on Linux CI. A green local e2e gave false confidence; the bug existed only on Linux. Two rules, both applied: (1) optional test corroboration must **degrade gracefully** (warn + skip), never hard-fail, when the primary proof already holds; (2) when CI must read an apiserver-written file, `chmod` it readable in the workflow. See `test/e2e/e2e_test.go` (`assertNoMutatingAudit`) + `.github/workflows/e2e.yml`.
